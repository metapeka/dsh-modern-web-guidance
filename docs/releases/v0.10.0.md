# 0.10.0 — whose numbers are these, and did the fix land? 🧭

0.9.0 taught a counter to explain itself. 0.10.0 makes it say **whose** numbers they are: scan counters
are partitioned per workspace, the last scan names its branch, and history answers "when did a rule fire"
and "is this site still there". Same four tools, same 33 rules, same `version: 1`, no new dependency.

## ✨ Features

- **The panel says which project it is showing.** A `Workspace: {name}` chip and a switcher sit in the
  header; `/guidance-stats --workspace <name|id|path>` and `--all` do the same from the command line.
  Scan counters are kept apart per workspace inside the one `stats.json`; guidance counters stay
  profile-wide, because a hit rate measures the corpus, not a directory.
- **The last scan names its branch.** A completed scan reads exactly `<workspace>/.git/HEAD` — one hop
  through a worktree's `gitdir:` pointer, a 1 KiB cap on each file, no `git` process, no enumeration —
  and prints `; branch main` or `; detached at a1b2c3d`. A failed read prints nothing at all: no
  "unknown" token, no guess ([ADR-0002](../adr/0002-branch-labels.md)).
- **Twenty scans of history, and one honest comparison.** `scanByDay` and per-rule first/last-seen
  dates answer "when", a 20-deep `scanHistory` answers "what the recent scans found", and a comparison
  line answers "did the fix land": `Since the scan of 2026-11-09 08:12: 3 no longer present, 82 still
  open, 1 new`. The report adds a five-row `Recent scans` block, the panel the same line and a last-seen date.

## 🧪 Behaviour changes

- **`/guidance-stats` defaults to the session's workspace**, not to every workspace: the unqualified
  number that mixed projects is the defect this release removes. With no session workspace it aggregates
  and says why; `--all` asks for the aggregate explicitly.
- **A site is compared by its hash, not by its line.** The key is FNV-1a over path, rule id and snippet,
  so a comment inserted above it changes nothing, and only eight hex characters are stored — a hash of a
  path, never a path, and never the snippet; an edited snippet is one site gone and one new, never a fix.
- **"Not comparable" is a first-class answer**, with seven guard tokens: `no-baseline`, `fewer-files`,
  `truncated`, `no-files`, `sites-unknown`, `branch-changed` and `rule-table-changed`. They print raw,
  like a skip reason, and the comparison then carries no numbers — never three zeros.

## 🛠 Hardening

- **Every addition is bounded**: history depth 20, ten rules per entry, four skip reasons, 200 site keys,
  40 diff rows, five rows on screen, one 1 KiB cap per file read, one `gitdir:` hop and nothing more.
- **One new read surface, and it only makes a label**: `.git/HEAD` is read on the completed-scan path
  only, never from an argument, and the scan tool's result and text are unchanged — the model sees no label.

## 🧩 Compatibility

- **`version` stays `1`.** The partition, the branch member and the history are additive, and a bump
  would be silent data loss: the normaliser reads any other version as an empty document. A 0.9.0
  document loads intact, its scan counters becoming the `_unattributed` bucket, named rather than hidden.
- **Version skew costs a line, never a row.** A host without the new fields renders the 0.9.0 panel and
  report exactly; an absent history, comparison or label renders shorter rather than as an invented zero.
  `engines` unchanged: DSH `>=0.2.0-rc.1 <0.3.0-0`, Node `>=22.19.0`.
