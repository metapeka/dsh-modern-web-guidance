# 0.8.0 — one ladder, one finding 🪜

A block of twenty legacy lines used to be twenty findings, because the scanner counted hits per line. It
now counts **code sites**: a run of one rule's hits on neighbouring lines is one finding, and every surface
prints the range it stands for. Same rules, same caps, same zero dependencies — and smaller numbers, which
are not the same thing as a cleaner project.

## ✨ Features

- **A finding is one place in the code.** Hits of one rule in one file collapse into a single finding while
  the next hit's line is at most `RUN_LINE_GAP = 2` lines after the previous one — the next line, or one
  blank line later. A wider gap, a different file or a different rule starts a new finding.
- **Every finding carries `lines` and `occurrences`, always.** A single hit is `lines: [154]` with
  `occurrences: 1`, so a consumer never needs a branch for the new fields, and `occurrences` is also
  `lines.length`.
- **The scan text prints a range instead of a line.** A single hit still renders `path:line:column` byte for
  byte; a run renders `path:first-last`, with `(N hits)` only when the run skips a line:

  ```text
  - src/components/Header.astro:642:5 ls-09 (medium)
  - src/components/ui/PostCard.astro:110-112 (2 hits) ls-12 (high)
  - src/styles/report-template.css:306-313 ls-05 (medium)
  ```

  `110-112` alone would claim three hits where there are two, hence the count; a dense run needs none.
- **The panel's chat row shows the same range** through one helper: `path:110-112` for a run and
  `path:2-4 (2)` when it skips a line, falling back to `path:line` when an older host sends only `line`.

## 🧪 Behaviour changes

- **Counts fall, and that is collapse, not repair.** The bench project's `src` (58 files) goes from **22
  findings to 10**, with `ls-05` from **13 to 2**: the eight-hit and five-hit ladders in
  `report-template.css` are now two findings. This repository goes from **97 to 85**. **22 line references
  existed before and 22 exist after** — nothing was lost, it was grouped. The 97 was never a quality metric
  (most of it is this repository's own rule table storing markers as data), and 85 is not "twelve problems
  fixed": a total that drops after upgrading says the counting changed, not the code.
- **`maxFindings` counts findings, not hits.** A 40-line ladder now costs one of the 200 slots instead of
  forty, so the same caps admit far more code. `SCAN_LIMITS` was not touched: nothing was widened, the unit
  changed.
- **Ordering follows the site**: path, then first line, then column, then rule id — a collapsed run sorts
  by where it starts, like any other finding.
- **`guides` counts findings too**, so the per-guide table stays consistent with the list above it.

## 🧩 Compatibility

- The two new fields are additive: `line`, `column`, `snippet` and `message` keep their meaning and now
  describe the **first hit** of the site, so code that printed `path:line:column` keeps printing something
  true. Nothing to change to keep working; use `lines` when you want the range.
- Rule messages were not rewritten to mention ranges — the range belongs to the finding, so a rule's text
  stays the one sentence it always was.
- The panel reads `lines` and `occurrences` defensively and falls back to `line`, so a client talking to an
  older host renders exactly what it used to.

## 📦 Package

- **256 files, 906 kB packed, 2.7 MB unpacked** (measured by `npm pack --dry-run`) — no file
  added or removed, still **zero** runtime dependencies, Apache-2.0, and **242 tests in 15 files** (241
  passed plus one symlink-walk test that skips itself where the host forbids creating symlinks).

- Находка теперь — **одно место в коде**, а не одна строка: серия попаданий одного правила на соседних
  строках схлопывается в одну находку, и все поверхности печатают диапазон.
- У каждой находки всегда есть `lines` и `occurrences`: у одиночного попадания `lines: [154]`,
  `occurrences: 1`, так что потребителю не нужна ветка для нового поля.
- Текст печатает `path:642:5` для одиночного хита и `path:110-112` для серии; `(2 hits)` появляется только
  там, где серия пропускает строку, иначе `110-112` соврало бы про три хита вместо двух.
- Числа падают: bench-проект `src` — **22 находки → 10**, `ls-05` — **13 → 2**; этот репозиторий —
  **97 → 85**. Это **схлопывание, а не починка**: 22 ссылки на строки были и остались 22, а меньшее число
  после обновления говорит о смене подсчёта, а не об очистке кода.
- `maxFindings` считает находки, а не хиты: лестница из 40 строк занимает один слот из 200. `SCAN_LIMITS`
  не меняли — изменилась единица измерения.
- Порядок — путь, первая строка, колонка, id правила; строка в чате показывает диапазон через тот же
  хелпер и терпит старый хост, у которого есть только `line`.

## 🇨🇳 中文摘要

<details>
<summary>展开</summary>

- 一条发现现在是一**处代码位置**，不是一行：同一规则在相邻行上的连续命中会合并成一条发现，各处文本都改为
  打印范围。
- 每条发现都带 `lines` 与 `occurrences`：单次命中即 `lines: [154]`、`occurrences: 1`，调用方不必为
  新字段写分支。
- 文本对单次命中仍打印 `path:642:5`，对连续命中打印 `path:110-112`；只有跨过一行时才追加 `(2 hits)`，
  否则 `110-112` 会把两次命中说成三次。
- 数字会下降：bench 项目的 `src` 从 **22 条变成 10 条**，`ls-05` 从 **13 变成 2**；本仓库从 **97 变成
  85**。这是**合并，不是修复**：行号引用更新前是 22 处，更新后仍是 22 处；升级后数字变小说明计数方式
  变了，不代表代码变干净。
- `maxFindings` 数的是发现而不是命中：40 行的连片命中只占 200 个名额中的一个；`SCAN_LIMITS` 未作改动，
  改的是计数单位。
- 排序为路径、首行、列、规则 id；聊天里的那一行通过同一个辅助函数显示范围，并在老宿主只给 `line` 时保持
  原有渲染。

</details>
